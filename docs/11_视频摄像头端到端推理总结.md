# Exp11 视频/摄像头端到端推理总结

## 1. 最终结论

状态：`PASS`

Jetson 已用同一个 C++17 程序完成以下串行链路：

```text
GStreamer 文件视频 / IMX219
→ OpenCV BGR 帧
→ CUDA 融合 letterbox + BGR→RGB + normalize + NCHW
→ FP16 TensorRT enqueueV3
→ 原始输出 D2H
→ YOLO11 解码 + 反 letterbox + class-aware NMS
→ CSV / JSON / 首末标注帧
```

文件视频 3 个独立进程均处理 150 帧、产生 151 个检测，逐帧检测 CSV 的 SHA256
完全一致。IMX219 30 帧 Smoke Test 和 300 帧正式功能验收均返回 0，采集、CUDA、
TensorRT、NMS 和输出合法性没有失败。因此 Exp11 功能链路通过，下一实验为 Exp12
性能、功耗、温度与稳定性测试。

## 3. 实现与同步边界

`CudaPreprocessor` 持久化输入/输出 device buffer 和 CUDA Stream。每帧先将 BGR
pageable host 数据 H2D，再在同一 Stream 上执行 Exp10 融合 kernel；返回的 device
输出指针直接绑定为 TensorRT 输入，不经过预处理结果 D2H 或额外 D2D。TensorRT 输出
仍需 D2H 供当前 CPU NMS 使用。

文件流显式使用 `qtdemux → h264parse → nvv4l2decoder → nvvidconv → appsink`，
`drop=false, sync=false`，用于尽快处理每一帧并保证确定性。实时 IMX219 使用
1920×1080@30、sensor-id 0，`appsink max-buffers=1 drop=true sync=false`，只保留最新帧，
防止消费者落后时队列无限增长。

YOLO11 原始输出按 `[cx, cy, w, h, person, helmet, safety_vest] × 8400` 解码；选择
最高类别分数后执行反 letterbox、边界裁剪和分类别 NMS。每帧都验证 raw 输出有限、
类别为 0～2、置信度在 `[0.25,1]`、框在原图内且面积为正。

## 8. 已证实、尚未证实与决策

已证实：文件和 IMX219 均能串行完成采集、CUDA、FP16 TensorRT、NMS 和结构化输出；
文件链路跨进程确定；实时流的单帧队列策略可运行；300 帧内无早停、NaN/Inf 或非法框。

尚未证实：多场景/多类别摄像头精度、零拷贝 NVMM→CUDA、异步重叠流水线、GPU NMS、
不同功耗模式、锁频后的公平性能、CPU/GPU/内存占用、功耗、温度、降频和长时间稳定性。
当前实现为便于审计，在 CUDA 预处理和 TensorRT 计时点同步；不能把阶段耗时简单与 Exp07
`--noDataTransfers + CUDA Graph + spin wait` 的 GPU-only 数字直接比较。

最终决策：Exp11 `PASS`，保持 FP16 主线。Exp12 在相同程序上冻结性能测试口径，采集
tegrastats/温度/功耗/占用、P50/P95/P99、丢帧和长时间稳定性，并区分当前同步基线与后续
流水线优化版本。

## 9. 快速学习与面试回答

为什么文件流和摄像头采用不同 appsink 策略？文件视频要逐帧可复现，所以不丢帧；摄像头
是无限实时流，若消费者短暂变慢，排队只会让结果越来越旧，因此用容量 1 的队列丢弃过期帧。

什么叫“CUDA 输出直接接 TensorRT”？融合 kernel 写入的 FP32 NCHW tensor 留在 GPU，
TensorRT Context 直接绑定该 device 地址；中间没有回 host，也没有再复制到另一个输入 buffer。

为什么 Exp11 的 31.415 FPS 还不是最终性能结论？它只是一段 300 帧、未锁频、当前场景下的
功能运行，且程序为分阶段计时进行了同步。最终结论还需 Exp12 固定功耗/时钟/计时边界，报告
分位数、资源、功耗、温度、丢帧和长稳态，而不是只报告一个 FPS。
