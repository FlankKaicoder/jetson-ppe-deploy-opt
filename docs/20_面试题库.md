# 面试题库与回答要点

## 一、项目与模型

### 1. 为什么最终仍使用原始YOLO11n，而不是P2或Attention模型？

因为候选必须同时通过相同数据划分、独立test、精度、复杂度和部署门槛。P2、重参数化、Attention/Focal都完成
公平消融，但综合条件未超过baseline。保留负向结果比事后降低门槛更能保证主线可信。

### 2. 为什么tiny+small recall单独报告？

PPE场景的关键难点是远距离安全帽/反光衣。全局mAP可能被中大目标掩盖；尺度召回能直接检查部署或量化是否让
细粒度候选跨过置信度阈值而消失。

### 3. 如何保证实验可复现？

冻结数据划分、权重/ONNX/Engine SHA256、阈值、输入尺寸和计时范围；使用实验分支、时间戳目录、返回码、JSON/
CSV摘要和三端串行Git流程。失败目录不删除，正式比较用paired/interleaved而不是挑最好轮。

## 二、ONNX与TensorRT

### 4. ONNX一致性只比较最终检测够吗？

不够。应同时比较raw tensor的max/mean absolute error和relative L2，再比较解码后的框、类别、置信度与模型级
指标。最终NMS可能隐藏raw差异，raw微小变化也可能在阈值附近放大。

### 5. Serialized Engine重复执行稳定，为什么同ONNX重新Build仍可能漂移？

前者固定了序列化Engine与tactic；后者重新触发TensorRT tactic selection、融合和数值路径选择。相同ONNX和
Builder参数不保证Engine或raw bitwise一致。跨Engine应估计普通rebuild variance并做检测级匹配。

### 6. 为什么主线选FP16？

FP16完整219图精度与PyTorch/FP32一致，GPU-only mean显著低于FP32，且后续C++ Runtime、CUDA和稳定性证据
完整。INT8虽更小更快，但旧implicit损害小目标召回；Explicit QDQ恢复精度后又没有性能Pareto收益。

## 三、CUDA与后处理

### 7. CUDA融合预处理具体融合了什么？

letterbox resize、padding、BGR→RGB、归一化和HWC→NCHW。对5种形状逐元素比较OpenCV参考，避免只在640×640
碰巧正确。kernel-only与包含pageable H2D的耗时分开报告。

### 8. CUB stable compaction为什么重要？

YOLO raw有8400个候选。先在GPU decode/filter，再稳定压缩有效候选，只回传count和payload，可减少D2H和Host
扫描；stable保证候选顺序确定，便于与CPU参考和冻结digest比较。

### 9. 为什么D2H减少99.89%，最终吞吐只改善3.64%？

D2H只是critical path的一部分；文件decode、H2D、TensorRT、同步、CPU NMS和DVFS仍存在。不同实验阶段的
19.19%与最终3.64%也不能相加。性能必须在相同编排下看端到端配对结果。

### 10. Double Buffer为什么失败？

它确实产生Kernel/Memcpy重叠，但重叠占比不足以覆盖CPU staging、资源竞争、队列与同步开销，P95明显恶化。
“有重叠”只证明机制发生，不证明critical path缩短。

## 四、Profiling与性能方法

### 11. `Host API Duration ≠ GPU Activity ≠ Critical Path`是什么意思？

Host API duration是CPU线程调用范围；GPU Activity是异步kernel/memcpy在设备上的执行；Critical Path是决定
一帧完成时间的依赖链。三者可能重叠或等待，不能简单相加，也不能把`enqueueV3` Host范围当GPU推理时间。

### 12. 为什么使用paired/interleaved？

Jetson动态调频、温度和后台状态会随时间漂移。相邻配对并交错顺序能减少把时间趋势误当代码差异；报告每对
变化、中位数和方向数，比独立平均或最好轮更稳健。

### 13. 为什么最终部署用动态调频？

动态调频代表真实默认部署。固定时钟可降低microbenchmark方差，但Exp12显示没有带来端到端收益且功耗增加
14.76%。因此固定时钟只用于诊断，不能替代最终主结果。

### 14. 为什么相机优化后仍是30 FPS？

IMX219输入本身是30 FPS，pipeline wall throughput受capture节拍限制。应拆分`capture_wait_ms`和
`post_capture_processing_ms`。Exp19中吞吐几乎不变，但处理阶段三轮均改善约1.77%。

## 五、量化、Plugin与Graph

### 15. INT8 tiny/small recall下降的机制是什么？

旧implicit INT8在P3 classification score产生较大误差，0.25阈值出现1138次向下穿越，使小目标候选在NMS前
消失；不是主要由类别argmax交换或严重clipping导致。Explicit QDQ把P3向下穿越降至93次。

### 16. 为什么Explicit QDQ精度更好却更慢？

显式Q/DQ带来reformat、量化/反量化节点和不同tactic；Jetson TensorRT 10.3下这些开销抵消INT8算力优势。
低精度算子存在、Engine更小或精度恢复都不能单独推出端到端更快。

### 17. Exp16是Plugin失败吗？

不是组件失败。IPluginV3、Creator/Registry、GraphSurgeon、显式workspace、独立进程dlopen→deserialize→
enqueueV3和同Engine数学语义都已验证。原系统Gate混入rebuild variance；重验证后语义通过，但性能无稳定收益，
所以是`IMPLEMENTED+VERIFIED+REJECTED`。

### 18. CUDA Graph局部指标很好，为什么仍拒绝？

Graph把每帧launch从67降到1，GPU gap下降93.4%，说明局部机制有效；但必须保留的H2D、count D2H/Host依赖、
payload D2H、CPU NMS和decode仍在Graph外。动态E2E三组只有1/3有利，采用Gate失败。

## 六、稳定性与工程判断

### 19. 54,000帧稳定性看哪些指标？

完整帧数和返回码、P95/P99及首末窗口漂移、wall throughput、温度、功耗、energy/frame、RSS增长/斜率、SWAP、
NaN/Inf和摄像头早停。只报告平均FPS无法证明稳定性。

### 20. 遇到RSS false positive如何处理？

保留原FAIL，定位到首个样本发生在Runtime初始化前；恢复Exp12预先冻结的第60秒稳态口径，对同一54,000帧
证据重新分析，而不是删除失败、重跑挑结果或放宽64 MiB/1 MiB每分钟门槛。

### 21. 项目最重要的工程原则是什么？

`Measure → Identify → Optimize → Verify → Re-profile → Accept/Reject`。功能能跑、Kernel更快、时间线有重叠、
Engine更小都只是局部证据；是否进入主线由冻结语义和系统级Gate决定。
