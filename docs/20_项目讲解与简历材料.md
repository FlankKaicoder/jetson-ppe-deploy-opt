# 项目讲解与简历材料

## 1. 30秒版本

我在Jetson Orin Nano Super上完成了一个PPE小目标检测的端到端部署优化项目。模型侧先用独立测试集冻结
YOLO11n baseline，再完成ONNX、TensorRT FP16和C++ Runtime一致性验证；部署侧实现CUDA融合预处理和GPU
decode/filter+CUB压缩后处理。最终动态调频Benchmark中文件吞吐配对中位提升3.64%，相机处理阶段提升1.77%，
并完成54,000帧、约30分钟稳定性测试，P95/P99为33.98/34.83 ms。项目也保留了INT8、Double Buffer、Plugin
和CUDA Graph等未被采用的结果，用Nsight和预冻结Gate决定是否进入主线。

## 2. 2分钟版本

项目目标不是只训练一个YOLO，而是把PPE小目标检测做成可复现的Jetson部署链路。数据和训练在AutoDL完成，
Windows负责Git与结果审计，Jetson负责TensorRT、CUDA、相机和板端Benchmark。

首先我对数据集和目标尺度做审计，训练并冻结YOLO11n baseline，独立测试集mAP50-95为0.5205，tiny+small
recall为0.7902。P2、重参数化、Attention和Focal都做了公平消融，但没有满足替换条件，所以没有为了“全PASS”
改门槛。之后完成PyTorch到ONNX、ORT一致性和Jetson TensorRT FP32/FP16验证，FP16 GPU-only mean为3.48 ms，
但我明确把这个数字和真实端到端延迟分开。

Runtime使用TensorRT 10.3 C++ API。CUDA融合预处理的kernel-only相对CPU参考下降91.2%；Nsight显示同步和D2H是
文件链路的重要瓶颈，于是把YOLO raw decode/filter放到GPU，用CUB稳定压缩候选，再只回传count和有效payload。
最终Benchmark中D2H由235,200 B/frame降到263.84 B/frame，文件wall FPS配对中位提升3.64%，相机由于30 FPS
输入限制，吞吐不变但post-capture处理阶段中位改善1.77%。最终版本完成54,000帧动态稳定性，P95/P99为
33.98/34.83 ms，最高温度57.03°C，SWAP无增长。

我还实现并验证了INT8、Double Buffer、IPluginV3、Explicit Q/DQ和CUDA Graph，但它们没有稳定通过精度或
系统性能Gate，因此没有进入主线。这部分最能说明我的方法：Measure→Identify→Optimize→Verify→Re-profile→
Accept/Reject，功能能跑不等于值得部署。

## 3. 5分钟讲解提纲

1. **问题与约束**：PPE小目标、Jetson资源有限、IMX219固定30 FPS；模型精度和部署性能分开验收。
2. **数据与baseline**：审计划分、尺度覆盖、独立test；冻结权重、哈希和阈值，结构消融不通过就保留负向结果。
3. **模型转换**：PyTorch→ONNX→ORT→TensorRT；解释FP16选择、Engine目标板构建和跨build tactic variance。
4. **Runtime正确性**：C++ TensorRT原始输出与Python参考逐字节一致；独立新进程验证生命周期。
5. **CUDA路径**：融合letterbox/颜色/归一化/layout；5种形状对OpenCV参考；区分kernel-only和含传输时间。
6. **Profiling**：Nsight拆分capture、H2D、preprocess、enqueue、D2H、NMS；Host API不等于GPU Activity。
7. **采用优化**：GPU decode/filter+CUB stable compaction保持候选顺序和NMS语义，显著压缩D2H。
8. **最终Benchmark**：动态paired/interleaved；文件报告最大吞吐，相机报告capture与post-capture；长稳态报告尾延迟、功耗、温度和RSS。
9. **负向决策**：INT8精度、Double Buffer尾延迟、Plugin/build variance、QDQ性能、Graph局部收益与E2E收益的区别。
10. **结论**：最终主线简单、可复现、证据完整；没有用复杂度换取不可重复的最好单轮数字。

## 6. STAR故事

### 故事A：为什么拒绝INT8

- **S**：INT8 GPU-only延迟更低、Engine更小，但小目标召回明显下降。
- **T**：判断问题来自校准覆盖、量化机制还是阈值附近误差，并决定是否采用。
- **A**：完成256图覆盖审计、implicit/Explicit QDQ区分、P3/P4/P5 score/bbox误差和threshold crossing统计，
  再构建粗粒度Mixed Precision候选并做219图精度与配对性能测试。
- **R**：确认旧implicit INT8在P3有1138次向下阈值穿越；Explicit QDQ降到93次并恢复精度，但GPU性能仍慢，
  因此保留FP16，避免用Engine更小掩盖系统收益失败。

### 故事B：为什么CUDA Graph没有进入主线

- **S**：Nsight显示launch overhead和GPU gap，Decision Gate允许实现Graph。
- **T**：证明局部timeline收益是否能形成真实端到端收益。
- **A**：只捕获device-side固定边界，验证150帧候选逐字节一致；节点级Nsight确认launch从67次/帧降到1次，
  再做三组动态paired/interleaved。
- **R**：launch API和GPU gap显著下降，但E2E仅1/3方向有利，故记`IMPLEMENTED+VERIFIED+REJECTED`。

## 7. 简历禁写清单

- 不写“INT8部署加速成功”；implicit精度失败，Explicit/Mixed性能失败。
- 不写“Double Buffer提升吞吐”；正式尾延迟严重退化。
- 不写“Plugin实现19%加速”；19%来自Exp15 CUB阶段，Plugin性能未通过。
- 不写“CUDA Graph端到端加速”；只证明launch/gap局部下降。
- 不把3.48 ms GPU-only写成摄像头端到端延迟。
- 不把kernel-only 91.2%下降写成整条Runtime提升91.2%。
- 不把30 FPS相机吞吐不变解释为优化无效或成功，必须报告post-capture和尾延迟。
