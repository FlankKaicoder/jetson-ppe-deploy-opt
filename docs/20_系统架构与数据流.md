# 系统架构与最终数据流

## 1. 三端工程架构

```mermaid
flowchart LR
    subgraph A["AutoDL · 模型与数据"]
        D["PPE 数据集审计"] --> T["YOLO11n 训练与消融"]
        T --> P["冻结 best.pt"]
        P --> O["ONNX 导出与 ORT 一致性"]
    end

    subgraph W["Windows · 项目总控"]
        G["Git / 文档 / 结果审计"]
        H["SHA256 与小型证据归档"]
    end

    subgraph J["Jetson Orin Nano Super · 部署"]
        E["TensorRT FP16 Engine"] --> R["TensorRT 10.3 C++ Runtime"]
        R --> C["CUDA preprocess"]
        C --> Q["enqueueV3"]
        Q --> U["GPU decode/filter"]
        U --> B["CUB stable compaction"]
        B --> N["CPU class-aware NMS"]
        N --> V["文件 / IMX219 输出"]
    end

    O -->|"ONNX + SHA256；Engine在目标板构建"| E
    A <-->|"代码与小型结果"| G
    G <-->|"GitHub 串行同步"| J
    H --- G
```

模型产物不通过普通Git传输；TensorRT Engine只在目标Jetson构建。Windows上的代码保存不等于AutoDL训练或
Jetson部署验证通过。

## 2. V_Final 单帧数据流

```mermaid
flowchart TB
    subgraph HOST["Host / CPU"]
        S["文件解码或 IMX219 capture"]
        HB["pageable BGR frame"]
        HC["读取 candidate count"]
        HP["按有效 count 接收 payload"]
        NMS["inverse-letterbox + class-aware NMS"]
        OUT["检测 CSV / 可视化输出"]
    end

    subgraph DEVICE["Jetson GPU"]
        DB["device BGR buffer"]
        PRE["CUDA fused letterbox\nBGR→RGB · normalize · HWC→NCHW"]
        TRT["TensorRT FP16 enqueueV3"]
        RAW["1×84×8400 raw output"]
        DEC["CUDA decode + confidence filter"]
        CUB["CUB stable compaction"]
        CNT["device candidate count"]
        PAY["compact candidate buffer"]
    end

    S --> HB
    HB -->|"H2D"| DB
    DB --> PRE --> TRT --> RAW --> DEC --> CUB
    CUB --> CNT
    CUB --> PAY
    CNT -->|"4 B count D2H + Host dependency"| HC
    HC -->|"决定可变 payload 大小"| HP
    PAY -->|"有效候选 payload D2H"| HP
    HP --> NMS --> OUT
```

最终路径保留同步的count读取和CPU NMS。Exp14 Double Buffer虽产生局部重叠但放大尾延迟；Exp16 Plugin、
Exp17 QDQ/Mixed和Exp18 Graph均完成实现或验证，但未通过系统级采用Gate，因此不在图中。

## 3. 计时边界

```text
GPU-only TensorRT：只回答Engine计算速度；不含真实输入、传输和后处理。
kernel-only CUDA：只回答Kernel本身；不含Host准备和传输。
post-capture processing：frame_total - capture_wait，适合分析30 FPS相机的可优化部分。
frame total / wall FPS：真实端到端结果，仍需结合输入节拍、DVFS和paired顺序解释。
```

任何结论均遵守：`Host API Duration ≠ GPU Activity ≠ Critical Path`。
