> 这是本项目从立项到收尾的统一学习入口，也是持续追加的实验学习日志。
> 它帮助项目完成后快速理解“为什么做、怎么验证、结果如何、下一步是什么”。

## 1. 使用方法

建议按三遍学习：

1. **10 分钟建立地图**：阅读第 2～7 节，先理解目标、三端分工、主线决策和关键指标；
2. **2 小时理解实验**：阅读第 8 节 Exp00～Exp07，重点理解每个假设为什么接受或拒绝；
3. **面试前复述**：阅读第 9～11 节，用自己的话讲出完整工程链路、指标边界和失败经验。

以后每个实验严格采用两条独立记录：

- 开始前在文末追加“实验前规划”；
- 完成后再追加“实验结果与学习复盘”，不覆盖旧计划。

## 2. 一句话认识项目

本项目在 PPE（人员、头盔、安全背心）小目标检测场景中，以 YOLO11n 为基线，
先用公平消融选择模型，再经过 ONNX、TensorRT、C++ 和 CUDA 完成 Jetson Orin
Nano Super 部署，最后用精度、延迟、吞吐、功耗、温度和稳定性共同验证工程价值。

它不是“训练出一个模型”就结束，而是回答四层问题：

| 层次 | 核心问题 | 主要证据 |
|---|---|---|
| 数据与模型 | 数据可靠吗，模型能检测 PPE 吗？ | 数据审计、P/R、mAP、尺度召回 |
| 结构选择 | 改模型是否真的优于基线？ | 固定划分和配置的消融实验 |
| 部署正确性 | 转换和低精度推理有没有改变结果？ | 张量误差、检测匹配、完整测试集 mAP |
| 系统性能 | Jetson 上是否真正更快、更省、更稳定？ | 端到端 P50/P95/P99、FPS、功耗、温度 |

## 4. 三端职责与 Git 串行流程

| 环境 | 主要职责 | 不能替代的工作 |
|---|---|---|
| Windows | 总控、阅读、文档、审查、合并、产物中转 | 不能声称训练或 Jetson 部署已验证 |
| AutoDL RTX 3080 Ti | 数据、训练、评估、PyTorch、ONNX、ORT、量化前准备 | 不能用服务器速度代替板端性能 |
| Jetson Orin Nano Super | TensorRT、CUDA、C++、摄像头、板端性能 | 不负责重新选择训练模型主线 |

推荐的串行 Git 流程：

```text
某一执行端创建实验分支并真实验证
→ push 实验分支
→ Windows 审查 diff、日志和文档
→ 合并 main
→ 另外两端 fetch/pull main
→ 下一执行端从新 main 创建下一实验分支
```

大型模型产物不进入普通 Git。代码和小型记录走 GitHub，`best.pt`、ONNX、Engine、
数据集和完整输出通过 `scp`/`rsync`/Windows 中转，并在发送端和接收端核对 SHA256。
TensorRT Engine 与具体硬件、TensorRT/CUDA 环境绑定，必须在目标 Jetson 重新构建。

## 6. 必须掌握的指标和概念

### 6.1 检测指标

- **Precision**：预测为目标的结果中，有多少是真的；误检越多，Precision 越低。
- **Recall**：真实目标中，有多少被找到；漏检越多，Recall 越低。
- **mAP50**：IoU=0.50 下各类别 AP 的均值，偏向“能否大致检测到”。
- **mAP50-95**：IoU 0.50～0.95 多阈值平均，更严格地评价定位与分类综合质量。
- **tiny/small recall**：直接检查业务关注的小目标是否被找回，不能被整体 mAP 掩盖。
- **固定阈值 P/R** 与 **AP** 不是同一指标：前者依赖一个置信度阈值，后者来自整条 PR 曲线。

### 6.2 模型转换

- **PyTorch**：训练和研究阶段的动态图模型；
- **ONNX**：跨框架中间表示，本项目冻结为静态 batch 1、640×640、FP32、外置 NMS；
- **TensorRT Engine**：为目标 GPU 和软件栈优化后的执行计划，不能跨设备直接复用；
- **FP32 / FP16 / INT8**：数值位宽逐步降低，通常更快更小，但必须验证精度损失；
- **PTQ**：训练后量化，不重新训练，通过代表性校准数据确定 INT8 量化尺度。

### 6.3 性能计时边界

GPU-only 只回答 Engine 内核执行速度，不等于用户看到的一帧总延迟。端到端通常包括：

```text
图像采集/解码 → CPU/GPU 预处理 → H2D → TensorRT → D2H → 后处理/NMS → 显示/输出
```

因此最终必须同时报告平均值、P50、P95、P99、FPS，并写清 warmup、迭代次数、Batch、
输入尺寸、功耗模式、`jetson_clocks`、是否包含预处理和数据传输。

## 8. Exp00～Exp07 学习复盘

### Exp00：项目初始化与范围冻结 — PASS

**核心问题**：如何让后续每次实验都可复现、可追溯且不覆盖历史？

建立仓库、Git/GitHub SSH、忽略规则、README、ROADMAP、项目范围、实验索引、模板和注册表。
最重要的成果不是某个指标，而是建立了“实验编号—分支—配置—日志—总结—决策”的证据链。

必须能讲清楚：大型模型不进普通 Git；失败实验也保留；在真实设备验证前不能写成 PASS。

### Exp01：Jetson 环境与编译链审计 — PASS

**核心问题**：板端的软件栈和 C++/CUDA/TensorRT 工具链是否真的可用？

确认 Jetson Orin Nano Super、aarch64、L4T R36.4.3、CUDA 12.6.68、cuDNN 9.3、
TensorRT 10.3.0.30、GCC/G++ 11.4、CMake 3.22.1、OpenCV 4.10、GStreamer 1.20.3。
CUDA 向量加法最大绝对误差为 0，TensorRT Runtime、OpenCV 和 GStreamer smoke test 通过。

关键失败经验：把全部代码放进 `.cu` 会触发 NVCC 与 GLib 宏冲突，最小修复是将普通主程序
交给 `g++`，CUDA kernel 单独由 `nvcc` 编译。另一个经验是 `trtexec --version` 在没有模型时
可能返回失败，不能只凭一个返回码判断 TensorRT 不可用。

### Exp02：数据审计与 YOLO11n 基线 — PASS

**核心问题**：数据集能否支持公平实验，原始 YOLO11n 的可靠基准是什么？

数据划分为 train 980 张、val 217 张/834 个目标、test 219 张/840 个目标，类别是 person、
helmet、safety_vest。审计发现并清理了一个重复标注。先做 1 epoch smoke test，再进行固定
seed=42、100 epoch、batch=16、AdamW 的正式训练，耗时约 717 秒。

独立 test 结果是 P=0.92161767、R=0.82040743、mAP50=0.89270104、
mAP50-95=0.52047856。固定阈值审计得到 GT=840、TP=731、FP=169、FN=109；
tiny recall=24/29=0.827586，small recall=89/114=0.780702，合计 0.790210。

关键失败经验：Shell heredoc、Python 标准输入和 `tee` 组合曾造成阻塞；预训练权重缺失也导致
smoke test 失败。正式长实验前的小测试能把这些工程问题提前暴露。

### Exp03：P2 小目标检测头消融 — REJECT

**实验假设**：加入 stride=4 的高分辨率 P2 检测头，可能提高 tiny/small 召回。

工程链路运行成功，但 test mAP50-95 从 0.52047856 降到 0.51273409，mAP50 从
0.89270104 降到 0.88405588；tiny recall 从 0.82759 降到 0.62069，small recall 从
0.78070 降到 0.75439。GFLOPs 从 6.4 增至 10.4（约 +62.5%），训练时间约 +16.1%，
RTX 推理约慢 30.4%，batch=16 的一次审计还触发 OOM。

结论：更高分辨率特征并不自动等于更好的小目标检测。数据规模、预训练适配、优化难度和计算压力
都会改变结果。因为业务关注的小目标更差且成本更高，所以拒绝替换基线。

### Exp04：部署可重参数化结构消融 — REJECT

**实验假设**：训练时使用多分支增强表达，部署前融合为单个 3×3 卷积，可能兼顾精度和速度。

分支融合在数值和检测指标层面几乎等价，证明“训练结构 → 部署结构”的转换工程是正确的。
候选模型 test mAP50-95 提升约 0.00275683，整体 Recall 也略升，但 tiny TP 从 24 降到 16，
tiny recall 从 0.82759 降到 0.55172。把阈值降到 0.001 也只恢复到 19 个 tiny TP，说明问题
不只是置信度阈值。

结论：重参数化转换 PASS，不代表候选模型可以进入业务主线。必须把“转换数值等价”“总体 AP”
和“关键尺度目标”拆开验收，因此最终 REJECT，但保留为重要的部署工程学习成果。

### Exp05：轻量注意力与 Focal 损失消融 — REJECT

**实验假设**：P3 残差式 CBAM-Lite 或 Focal 分类损失可能提升难样本和小目标表现。

注意力只增加 4,259 个参数（约 +0.1644%），mAP50-95 仅增加 0.00008167，
tiny+small recall 却下降 0.034965。Focal 的 mAP50-95 增加 0.006459，但 mAP50 下降
0.012815，tiny+small recall 下降 0.083916。两个单变量都没有通过门槛，因此按预设停止规则
跳过 attention+focal 组合，避免无效算力消耗。

结论：总体 AP 小幅提升不能代替业务关键尺度指标；停止规则必须在看结果之前设定。

### Exp06：PyTorch → ONNX 与一致性验证 — PASS

**核心问题**：冻结基线能否转换成 TensorRT 可接收的 ONNX，并保持数值和检测语义一致？

导出静态 FP32 ONNX：batch=1、640×640、opset 17、dynamic=false、simplify=false、外置 NMS。
模型通过 ONNX checker 和 ONNX Runtime 前向。单图原始输出 max abs error=0.00061035、
mean abs error≈1.03e-5、relative L2≈1.27e-7；30 个检测的数量和类别完全一致。
完整测试集在相同 `rect=false`、batch=1 条件下，PyTorch mAP50-95=0.51376814，
ORT=0.51385152，差值 +0.00008338。

关键经验：导出成功不等于部署正确；至少要验证模型结构、原始张量、NMS 后结果和完整数据集 AP。
曾遇到 NMS 导入错误、Shell 语法、平均误差阈值过严、`rect` 配置不一致，以及错误地用同一个
置信度阈值计算 P/R 和 AP，这些都通过缩小失败点后修复。

### Exp07：Jetson TensorRT FP32 / FP16 — PASS

**核心问题**：ONNX 能否在目标 Jetson 构建并运行，FP16 是否在保持检测精度时获得收益？

FP32 和 FP16 Engine 均在 TensorRT 10.3 的目标 Jetson 本机构建，完成单图、完整测试集和
GPU-only 诊断 benchmark。FP16 约为 FP32 的 2.943 倍，Engine 小约 39.84%；同运行时
完整测试集 mAP50-95 与 PyTorch/FP32 参考基本一致，因此 FP16 成为后续运行时主选，FP32
继续作为正确性参考。

关键失败经验包括：SSH 输出管道提前关闭导致 SIGPIPE；FP16 原始误差阈值过严；自动依赖安装
长时间停滞；不同 Ultralytics 版本的 AP 口径不可直接比较；在同一进程顺序加载多个 Engine 引发
CUDA context 清理错误。最终使用同一个 Jetson 验证器、各后端独立进程、公平固定预处理和
后处理完成验证。这里的 GPU-only 数值仍不是端到端性能。

## 9. 当前可复述的项目讲解

### 60 秒版本

我做的是一个 Jetson Orin Nano Super 上的 PPE 小目标检测与推理优化项目。项目先审计数据，
训练并冻结 YOLO11n 基线，再对 P2 检测头、可重参数化、轻量注意力和 Focal loss 做固定数据划分
的单变量消融。部分方案总体 AP 略有改善，但 tiny/small 召回变差或计算成本显著增加，所以没有
为了“有创新点”强行替换基线。之后我把冻结模型导出为静态 ONNX，通过原始张量、NMS 后检测和
完整测试集 mAP 验证 PyTorch/ORT 一致性，再在 Jetson 本机构建 TensorRT FP32/FP16 Engine。
FP16 在 GPU-only 计时中约加速 2.94 倍且大小降低约 39.84%，完整测试集精度基本保持。INT8 PTQ
又获得约 25.44% GPU-only 延迟下降和约 39.82% Engine 缩小，但 mAP50-95 与 tiny+small recall
超过预冻结退化门槛，因此没有为了速度牺牲关键尺度检测，部署主线保留 FP16。之后用 TensorRT
10.3 C++ API 实现 Runtime，三独立进程的原始输出都与 Python 参考逐字节一致。下一步继续 CUDA
预处理和包含功耗温度的端到端测试。

### 必须避免的夸大

- 不能说 P2、注意力或 Focal 提升了最终模型，它们的最终决策是 REJECT；
- 不能把 3.4797 ms 直接说成摄像头实时端到端延迟；
- 不能说 INT8 已被部署主线采用，也不能说 CUDA 融合、功耗温度测试已经完成；
- 不能用 RTX 3080 Ti 的速度代表 Jetson；
- 不能把 Engine 构建成功等同于精度验证成功。

## 10. 高频面试问题

### 为什么最终仍使用原始 YOLO11n？

因为替换条件是综合验收，不是只看一个总体指标。P2 使关键指标和成本都变差；重参数化候选虽有
轻微 mAP50-95 增益，但 tiny recall 大幅下降；注意力和 Focal 也损害 tiny+small recall。
原始基线在当前数据和业务目标下更稳健。

### 为什么 ONNX 要做四层验证？

checker 只证明图结构合法，前向成功只证明能运行；原始张量比较检查数值，NMS 后比较检查检测
语义，完整测试集 AP 才检查误差是否会积累成业务影响，四层关注点不同。

### 为什么 FP16 更快但还需要 FP32？

FP16 利用 Jetson 的低精度硬件路径，通常更快更小；FP32 数值误差更小，是定位转换或量化问题的
正确性参考。只有验证 FP16 的最终检测和数据集指标后，才能把它作为部署主选。

### 为什么 INT8 需要校准集？

激活从浮点映射到 8 位整数需要合理的数值范围。校准集要代表真实训练分布，并复用完全相同的
预处理；不能使用测试集，否则会造成评估泄漏。校准数量不是越多越好，应通过预先设计的消融冻结。

- **融合内容**：一个二维 CUDA Kernel 完成 half-pixel letterbox resize、114 padding、BGR→RGB、
  uint8→FP32 `/255` 和 HWC→NCHW；输出固定为 `[1,3,640,640]` 连续 device tensor。
- **正确性**：square、wide、tall、hd_wide、small_tall 的 max/mean/relative-L2/P99/padding
  误差全部为 0；所有几何、形状和有限值检查通过。
- **性能**：`hd_wide`、warmup 20 + 200 次时，CPU/kernel-only/pageable total mean 为
  2.282124/0.200761/1.883069 ms；kernel-only 比 CPU 下降 91.2029%，通过预冻结 30% 门槛。
- **为什么 total 不是核心门槛**：total 把输入传到 GPU，又把 4.9 MB FP32 输出传回 CPU；实际
  TensorRT 流水线应让预处理输出留在 GPU，所以 kernel-only 才反映即将连接的 device 流程。
- **关键失败 1**：第一次 CMake 在非登录 SSH 环境找不到 CUDA compiler；显式使用
  `/usr/local/cuda/bin/nvcc` 修复，没有重装或修改系统 CUDA。
- **关键失败 2**：朴素双线性在 4/3 放大时只有 1 灰度级误差，但 relative L2 超过门槛；普通
  11-bit 合并定点和“半整数统一向下”两种修复假设也失败，所有目录均保留。
- **真正根因**：OpenCV 4.10 的 CV_8U `INTER_LINEAR` 专用纵向路径会在两阶段定点运算之间截断
  中间位。要逐像素一致，必须复现运算顺序和中间截断，不能只实现数学上等价的双线性公式。
- **工程经验**：优化代码的黄金参考不仅包括几何公式，还包括数据类型、量化系数、边界、舍入、
  中间精度和平台 SIMD 路径；误差很小也必须按事先门槛决策。
- **尚未证实**：本实验没有把 device tensor 直接绑定 TensorRT，没有验证摄像头、NMS、端到端
  延迟、功耗、温度或稳定性；这些属于 Exp11～Exp12。
- **面试回答**：CUDA 预处理为什么需要 CPU Reference？因为颜色、letterbox、布局或 1 灰度级
  舍入差异都会改变模型输入。应先逐元素证明语义等价，再分开报告 kernel 与传输时间，最后才接入
  TensorRT 测端到端收益。
- **下一步**：Exp11 在 Jetson 串行连接 GStreamer/视频帧、CUDA 预处理、Exp09 FP16 C++ Runtime
  和检测后处理；预先冻结队列、丢帧、同步、延迟与摄像头不可用时的文件视频替代规则。

  消融把 pinned、Event 和 buffering 的效果拆开，为 Exp15 是否把 CPU 后处理移到 GPU 提供证据。
